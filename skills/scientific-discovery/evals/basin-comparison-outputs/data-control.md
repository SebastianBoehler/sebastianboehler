## Decision rules

1. **First validate the comparison.** If logs do not establish which artifacts produced the reported scores, label the scores unverified. If the snapshots, revisions, or preprocessing cannot be recovered, do not reconstruct them from memory. Document the missing provenance and request the specific artifacts or rerun a known configuration later. An existing checkpoint may permit evaluation, but it cannot recover missing training history.
2. **Choose the bottleneck from measured end-to-end work.** Rank stage times and check whether the observed bottleneck persists across representative batches. A low utilization reading alone does not establish the cause. If instrumentation or duration is insufficient, report the dominant stage as unresolved and propose the cheapest measurement that would resolve it. A short benchmark supports a conclusion only about that measured slice; include startup, epoch boundaries and validation separately when relevant.
3. **Treat speed and score as separate questions.** The same held-out metric and split must be used for comparisons. If evaluator, target units, masks, aggregation, or split differ, restore parity before interpreting scores. If all three historical factors differ, even validated historical results cannot isolate a cause. A matched, one-factor test can discriminate one hypothesis within the tested context; if randomness or only one run prevents a reliable comparison, report uncertainty and avoid claiming a general improvement. Do not infer full-training quality from a short timing test.
4. **Choose the next action conditionally.** If input loading dominates and traces show waiting, test a specific loading change under the same data and work. If preprocessing dominates, inspect repeated or avoidable work before proposing a targeted change. If training dominates, profile the relevant operations before considering a compute change. If evaluation or checkpointing dominates, inspect its frequency and cost without weakening the evaluation protocol. If numerical or data checks fail, correct or investigate that issue before interpreting performance. If evidence does not discriminate, recommend the missing measurement rather than a speculative fix.
5. **Keep experiments valid.** Capture code revision, data snapshot identifiers, preprocessing configuration, split and evaluator version, seed, device and software, timing boundaries, sample/step counts, peak memory, raw outputs and commands. Use the same workload for speed comparisons, and preserve enough evidence to repeat them. Stop any test that approaches the machine's memory limit. The 64 GB RAM and an unspecified GPU do not establish available GPU memory.

## Assistant brief

**Objective:** Independently inspect the local data and execution path, then produce a reproducible, bounded stage-timing report. Your allotted work is 85 engineering-minutes: 25 for data/code inspection, 25 for benchmark setup and correctness checks, and 35 for profiling. Tell the coordinator promptly if an artifact is missing or a stage cannot be measured.

**Inputs:** The coordinator will supply the old and new run artifact paths, dataset/split paths, repository revisions, metric and evaluator entry point, if present. Inspect both runs' actual settings and artifact provenance rather than relying on the chat description. Identify the dataset's source and measurement process from available local documentation; record if undocumented. Check units, labels, masks, missingness, preprocessing fit boundaries, temporal/spatial split construction, inference-time information, and likely confounds. Do not access external services or share data.

**Procedure:** Work in an isolated directory. Treat inputs and historical runs as read-only. Do not delete or overwrite them. Start with a small batch to validate shapes, finite values, target units, preprocessing and metric inputs; compare against trustworthy existing outputs if available. Report any check you cannot perform. Build a representative, repeatable benchmark with the existing evaluator and workload where possible. Measure warm-up separately, end-to-end elapsed time, stage elapsed times, workload size, and peak memory; add repeated paired runs only within your cap. GPU operations can be asynchronous, so synchronize relevant timed regions and describe the timing method. Avoid presenting a profiler's instrumented total as an uninstrumented end-to-end time. If full-run artifacts are unavailable, distinguish a new partial benchmark from the historical runs.

**Deliverable:** Return a concise inventory and a table for each observed stage with measurement method, workload, timings or explicit missing status, memory, and limitations. Give exact paths to isolated logs and commands, identify validated versus unverified provenance, and flag numerical, leakage, and evaluator concerns. List competing explanations and the smallest controlled next check. Do not call any proposed mechanism a measured result, claim a whole-run improvement from a short slice, change the split, exceed memory, or choose a GPU optimization without evidence.
