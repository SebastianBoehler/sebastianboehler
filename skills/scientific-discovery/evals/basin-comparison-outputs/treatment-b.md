# A. Cell segmentation across hospitals

**Decision.** The 50 runs explore one RGB U-Net pipeline; they do not establish that all representations were tried. The self-supervised approach never trained, so it is an execution failure, not a negative result. Resampling tiles from the four hospitals does not create a sixth independent hospital. The proposed wave tests two concrete changes to the inherited pipeline, subject to an eight GPU-hour cap.

**Access and assumptions.** Use images and annotations from the four development hospitals only for model development and selection. Use the fifth hospital exactly once for the frozen final evaluation, with no changes in response. No new annotations. Hospital is the split and independent evaluation unit; keep all tiles, overlapping crops and derived images from a patient or hospital in that hospital's partition. Check patient identities across hospitals if available. Assume the existing evaluator defines cell matching and mean F1; inspect its implementation and preserve that definition, handling missing hospital identifiers or ambiguous matches before scoring. The number of images, annotation quality, stains, acquisition differences, source code and actual training times are not supplied and must be checked; none is treated as established.

| Family / mechanism | Coverage and uncertainty | Next test |
|---|---|---|
| RGB supervised U-Net | Fifty augmentation, learning-rate and seed refinements; hospital-disjoint validity and exact run provenance need inspection. Fixed threshold is inherited. | Reproduce the best valid configuration with common folds. |
| Color-normalized representation with same U-Net | Proposed, not evaluated; may reduce acquisition or stain variation, but could erase useful cell information. | Fit normalization using training hospitals only; compare against RGB with the same model, labels, training and evaluation. |
| Multiscale supervised input with coherent U-Net prediction | Proposed, not evaluated; added context may help distinguish crowded cells, though gains could reflect added compute. | Compare full end-to-end multiscale inference to RGB and record capacity and actual compute. |
| Self-supervised representation | Failed before training; not evaluated. | Keep open; defer repair until this wave's evidence and budget justify it. |

**Evaluation and eight-hour allocation.** First inspect image generation, units, annotation protocol, duplicates, missing labels and evaluator provenance. Use four leave-one-hospital-out development folds: train on three hospitals and score the fourth; ensure all candidates see the same folds and training rules. Use the incumbent fixed threshold as the primary matched comparison. As a secondary, selection-only analysis, choose a common threshold from out-of-fold development predictions and clearly label the resulting development score as selected on those predictions. Do not tune on the final hospital. Predefine a fit failure or an out-of-memory run as invalid, not as a negative scientific result.

- **2.5 GPU-hours:** reproduce the RGB baseline across all four folds, including a short timing and data-path check. Reuse verified predictions only if their source, split and configuration match.
- **2.5 GPU-hours:** evaluate color normalization across the same four folds; fit normalization separately inside each training fold.
- **2 GPU-hours:** evaluate an end-to-end multiscale supervised model on the same folds, with controlled capacity and report the compute difference.
- **1 GPU-hour:** reserve for a narrowly diagnosed repair and the final retraining/evaluation of the selected configuration. Limit a failed new-method repair to 0.25 GPU-hour; retain the rest for final training. CPU-based inspection and scoring do not count against the GPU cap.

A timing pilot must establish that a complete four-fold comparison and final retraining fit. If they do not, drop multiscale first and devote its budget to completing the baseline and normalization across all folds; if even that fails, report incomplete evidence instead of ranking partial folds. Select by hospital-mean F1, show each hospital and a hospital-level uncertainty interval, and disclose the four-hospital sample and repeated-selection limitations. Hypothesis, not measured headroom: normalization or multiscale might change mean F1 by roughly −2 to +2 percentage points; a small apparent gain with wide uncertainty is inconclusive. If the alternative underperforms consistently, that specific implementation is disfavored, not the entire family. Freeze the selected training recipe and threshold, train on the four development hospitals, then score once on the fifth; report that single-hospital result separately from development selection. The wave broadens actual evidence only if a changed representation is implemented and validly evaluated.

# B. Day-ahead load forecasting

**Decision.** The 80 runs tune separate per-site trees with a fixed 24-hour window. The shared model is untested because its site-ID loader failed. The next wave compares a valid shared quantile model with the incumbent and tests longer history, under the production deadline.

**Information and assumptions.** Each forecast predicts the next day's hourly 90th percentile for 300 sites. Past loads and calendar features are available; future actual temperature is prohibited. Forecast temperature may be used only if historical forecasts with their original issuance times are available at each backtest origin. If not, omit temperature for all compared models rather than substituting actual future weather. Check timestamps, time zones, daylight saving, site identity, missing loads, changed meters and forecast issuance; do not impute using future information. The five-minute limit covers the production forecast path for all sites on the specified CPU server; assume model fitting happens outside that forecast deadline, and report its cost separately. Verify this assumption before execution.

**Matched protocol and four CPU-hours.** Use identical chronological rolling-origin development windows before the reserved final month, with multiple weekly or longer validation blocks as runtime permits. Train only on observations available before each origin, generate all day-ahead horizons without future loads, and use identical sites, origins, feature availability and mean pinball-loss calculation. Verify that the evaluator uses the 0.9 quantile, reports per-site and aggregate scores, and handles missing data identically. Fix candidate settings and selection rules before scoring. Save per-origin predictions, dataset version, source revision, commands, seeds and timing scope.

- **1.25 CPU-hours:** reproduce the incumbent across the chosen origins and inspect data/evaluator paths.
- **1 CPU-hour:** run the shared model using the same features and origins; include a quick check that site IDs are nonmissing, vary across sites and reach the fitted model.
- **0.75 CPU-hour:** run the longer-history per-site model on the same origins.
- **0.5 CPU-hour:** reserve for final refitting and the one-time final-month evaluation of the frozen choice.
- **0.5 CPU-hour:** measure the complete forecast path on the production-equivalent server, including feature construction, model loading, predictions for 300 sites and required output, with the real thread count, I/O, peak memory and warm and cold timings. Include the incumbent and any candidate eligible for selection.

Pilot costs first. If the full matched protocol and final refit cannot fit, reduce the number of origins equally across all candidates and use contiguous, preselected blocks; never compare scores from different periods as a direct win. Record total cost and stop at four hours. If a valid final refit cannot fit the reserve, report it as not completed rather than exceeding the cap. Compare paired loss differences aggregated across sites by time block; report a block-based interval that respects temporal dependence and shared weather effects. Multiple model choices and limited independent blocks make small improvements uncertain. An illustrative prior is −3% to +3% relative loss versus the incumbent, not a measured expectation. A negative result disfavors the tested configuration only. If site IDs fail the data-path check, repair within its allocation or mark the shared-model experiment invalid; do not claim a scientific failure.

Choose the lowest validated development loss only if its complete forecast path meets five minutes with headroom across repeated representative measurements. Otherwise prefer the incumbent, provided the incumbent itself meets the deadline; also retain it when the candidate gain is too uncertain to justify replacement. If no candidate meets the deadline, report the constraint unmet. Freeze the choice, refit using permitted pre-final data, and evaluate the untouched final month once; distinguish final-month accuracy from development selection and production behavior. Any benefit from shared learning, longer history or forecast weather remains hypothetical until these tests complete.
