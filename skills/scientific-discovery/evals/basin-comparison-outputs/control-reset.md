Preserve the existing running job, its pinned snapshot, the validated best six-element artifact and the canonical ledger. The coordinator retains the requirements, job, ledger and final decisions. No external providers or spending are available. The six-element lock has no documented basis and is a challengeable design decision, not a simulator requirement. If clean contexts cannot be established, label this a same-context critique, not a demonstrated reset.

After problem-first proposals, give both assistants the validated incumbent and actual ledger evidence. # E — Four engineering-hours for inference speed

**Assumptions.** Four engineering-hours means four aggregate person-hours across the coordinator and two assistants, not four hours each. Work takes place in isolated copies on the existing machine. The service and production source remain untouched. The fixed production batch is the primary decision workload; other supplied batches are correctness checks where compatible with the same input/output contract. The 120 ms figure is an existing end-to-end observation, not yet a controlled baseline. No optimization or measurement below has run.

**Success condition.** Find the lowest reliably measured end-to-end latency for the same work and input/output contract, with every output numerically equivalent to the pinned CPU reference within absolute tolerance 1e-5. If no candidate passes both correctness and a repeatable practical speed comparison, keep the current CPU path. A small apparent gain within measurement uncertainty is inconclusive. Any eventual deployment is outside this study.

**Allocation and worker briefs.** Times include planning, inspection, implementation, timing and result recording; parallel elapsed time may be shorter than four hours.

| Work | Owner | Engineering-hours | Concrete deliverable |
|---|---|---:|---|
| Freeze reference and measure baseline | Coordinator | 0.50 | Record model, inputs, software and hardware identities; run correctness and timing harness, capture component breakdown, variance, memory and thread settings |
| CPU optimization | Assistant A | 1.25 | Inspect the breakdown, try a bounded thread/affinity sweep and one bottleneck-directed change in an isolated copy; return source/config, accuracy, paired timings and memory |
| GPU complete path | Assistant B | 1.25 | Implement or repair one isolated complete path including setup, transfers, preprocessing, inference and output transfer; return source/config, output checks, paired timings and memory |
| Compare, diagnose, and record recommendation | Coordinator | 1.00 | Independently validate promising candidates, repeat paired timing and document the decision and limits |
| **Total** | | **4.00** | |

The coordinator starts the common reference and shares its immutable inputs, model, harness and contract with both assistants. Assistant A may inspect and prepare while baseline measurements run; Assistant B must not wait on CPU-specific optimization. Both report failures promptly and stop unpromising repairs rather than consume the comparison budget. Time spent coordinating counts against the coordinator allocations.

**Measurement protocol.** Record the exact pinned model and input hashes or versions, code revisions, dependency versions, CPU/GPU model, operating conditions, batch shape, precision, thread count and affinity, memory use, and whether the machine is shared. Instrument preprocessing, setup, transfers, inference and output handling without changing the timed work. Measure the complete service-equivalent boundary from identical ready inputs through the returned output, including any required device synchronization and transfers. For a persistent service, report steady-state warm latency and one-time cold initialization separately; also include setup in end-to-end latency when the actual service pays it per request. The same boundary and output work apply to all paths.

Start with 10 warm-ups, then five blocks of 10 paired reference/candidate measurements, alternating execution order. Adapt the count only if the remaining budget or observed variability requires it, and record the change. Compare per-block paired differences and report median latency, spread and a confidence interval over independent measurement blocks; report p95 only with the sample-size limitation. Investigate throttling, concurrent load and timing outliers instead of silently deleting them. Re-run the best candidate in the coordinator's isolated environment with the same settings. Track peak host and GPU memory and transfer costs; a faster kernel alone does not establish a faster pipeline.

**Correctness and choice.** For the fixed batch and available compatible inputs, compare each complete output with the CPU reference: identical input/output structure, shape and required dtype, finite/nonfinite behavior, and elementwise absolute difference ≤1e-5. Report maximum absolute error and the location/count of violations. Check repeatability and output after warm-up; a faster path with an error fails, even if average error is small. Verify that the candidate actually runs the intended code and performs the same work. Investigate unexpected discrepancies before timing claims.

Compare the current CPU, best validated CPU candidate and validated GPU candidate under the same full boundary. Choose a candidate only when its complete path passes correctness and its paired latency improvement is repeatable beyond measurement noise, with memory and setup compatible with the service. If the GPU fails equivalence, has no reliable end-to-end gain, exceeds available memory, or its setup makes the actual workload slower, keep the best validated CPU path. If the optimized CPU candidate also lacks a reliable improvement, keep the original CPU path. Record raw measurements, configurations, failed candidates, uncertainty and remaining time limits.

**Unsupported conclusions.** The 30 ms GPU number measures only a kernel. It does not establish GPU end-to-end latency, a 4× speedup, correct outputs, memory feasibility, or production benefit. The existing 120 ms CPU figure has no measured variance or thread settings, so it does not yet establish a fair baseline or attainable speedup.
